# Микросервисная система бронирования мероприятий (Event & Booking App)

Данная система представляет собой распределенное приложение на базе .NET 8, построенное по принципам Clean Architecture. Взаимодействие между микросервисами осуществляется асинхронно через брокер сообщений Apache Kafka.

---

## 1. Состав системы (Архитектура и порты)

Инфраструктура системы (СУБД, Брокер, Сервисы) развернута в Docker-контейнерах

| Сервис / Компонент | Назначение | База данных (Docker) | Внешний порт |
| :--- | :--- | :--- | :--- |
| **User Service** | Аутентификация, выдача JWT, роли | `users` (PostgreSQL) | `5441` (БД) |
| **Event Service** | Управление мероприятиями и местами | `events` (PostgreSQL) | `5442` (БД) |
| **Booking Service** | Оформление и подтверждение броней | `bookings` (PostgreSQL) | `5443` (БД) |
| **Apache Kafka** | Распределенный брокер сообщений | — | `9092` (Брокер) |
| **Zookeeper** | Координатор для Apache Kafka | — | `2181` (Служебный) |

### Пошаговый процесс:
1. **Публикация (Booking Service)**: 
   * Фоновый обработчик меняет статус брони на `Confirmed` и фиксирует изменения в своей базе данных `bookings`.
   * Сразу после этого компонент `IBookingEventPublisher` сериализует контракт `BookingConfirmedEvent` в JSON и отправляет его в топик Kafka `booking-confirmed`.
   * **Важно**: В качестве ключа сообщения передается `EventId`, что гарантирует попадание всех броней одного мероприятия в одну партицию Kafka и их последовательную обработку.

2. **Получение и обработка (Event Service)**:
   * Фоновый сервис `BookingConfirmedConsumer` слушает топик `booking-confirmed` в бесконечном цикле.
   * При получении сообщения открывается атомарная транзакция базы данных.
   * **Идемпотентность (Inbox Pattern)**: Сервис через `IInboxRepository` пытается сохранить `BookingId` и имя события в общую таблицу `inbox_messages` (используется составной ключ `id_booking + message`). Если запись уже существует — база отклоняет её, сообщение признается дубликатом и пропускается без изменений.
   * **Бизнес-логика**: Если сообщение уникально, вызывается `IEventService.TryReserveSeats()`. Сервис находит мероприятие в БД `events` и уменьшает количество доступных мест (`AvailableSeats`) на один.
   * **Фиксация**: Транзакция подтверждается (`CommitAsync`), и оффсет сообщения фиксируется в Kafka (`Commit(consumeResult)`).

## 3. Инструкция по запуску системы

### Шаг 1. Запуск инфраструктуры (Docker)
Убедитесь, что Docker Desktop запущен. Находясь в корневой папке проекта (где лежит файл `docker-compose.yml`), выполните команду:
```bash
docker compose up -d
```
*Контейнеры баз данных, Kafka и сервисы поднимутся в фоновом режиме, порты пробросятся локально. *

### Шаг 2. Применение миграций EF Core
Миграции к БД применятся автоматически.

### 3. Открытие Swagger UI в браузере:
Каждый сервис предоставляет собственную интерактивную документацию API. Откройте следующие ссылки в браузере:
* **User Service API**: `http://localhost:5001/swagger` — регистрация пользователей, аутентификация и получение JWT-токенов.
* **Event Service API**: `http://localhost:5002/swagger` — просмотр и управление мероприятиями (требует JWT-токен с ролью Admin для записи).
* **Booking Service API**: `http://localhost:5003/swagger` — создание и подтверждение бронирований (требует JWT-токен авторизованного пользователя).
